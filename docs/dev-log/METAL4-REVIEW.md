# Cadence Metal 4 facade (mcm4.m) review

Code reading only, plus six small standalone probes in this directory (xcb.m, ret.m, tbl.m, tbl2.m, rs.m, layer.m, fence.m, samp.m). No repository file was edited, no Gradle/Minecraft run.

Bottom line: I found no missing barrier and no missing residency for anything the shipped (non-opt-in) paths do. The synchronisation and residency design is sound and the places I attacked hardest held up (see "Checked and OK" at the end). The real bugs are about lifetime of objects that Metal 4 does not retain, one hard crash on an opt-in path, one residency-set side effect that starves the recorder, and a handful of semantic gaps for addons. Highest value first.

## A. Bugs

### A1. MTL4 command buffers do not retain pipeline states: pipeline-cache eviction is now a use-after-free (medium, reachable only past 64 layouts)
Evidence (ret.m): encode a draw and a dispatch with a render and a compute pipeline, drop every reference before commit: both pipeline objects are deallocated (weak refs go nil). Metal 3 retained them in the command buffer (that is why `[pso release]` right after encoding used to be safe); the facade/rset only retains resources, never pipelines, samplers, depth-stencil states, fences or MetalFX scalers.

Sites that release a pipeline while the current frame's (uncommitted) or an in-flight frame's commands can still reference it:
- mcown.m:644-648 (`ownPipeline`): when `layoutCount == OWN_MAX_LAYOUTS (64)` it does `[w->layouts[0].pso release]`. layouts[0] is the oldest layout, typically a common solid/cutout layout that is drawn every frame.
- mclod.m:211-215 (`colPipeline`): same eviction with LOD_MAX_LAYOUTS.
- lodseam.m:225: `[s->tilePso release]` when the colour format changes mid-frame (opt-in taaTile).
Scenario: 64 distinct (attachment-format x kind-bits) combinations are reached (kind bits 0-30 are variant flags: half/lean/tight/mesh/occ A/B/exact/group..., times main target vs shader-pack G-buffer formats). The 65th evicts layouts[0]; the pipeline is freed while 1-3 frames in flight (and the open encoder) still point at it; GPU executes freed pipeline state: garbage frame, page fault, or CB error.
Fix: never evict (grow the array), or move evicted pipelines to a "dying" list released only when `completed >= submitted + 1` (the same gate mcm4.m already has for resources). Same for `tilePso`.
Java side is fine here: MetalPipeline.close uses `releaseLater` (MetalPipeline.java:582-585), MetalCompute kernels too.

### A2. VideoToolbox recorder starves its own pixel-buffer pool under Metal 4 (medium, -Dcadence.rec with the vt codec only)
rec.m:443-492 `mcr_vt_capture` creates two CVMetalTextures per recorded frame, binds the IOSurface textures with `[ce setTexture:yt/uvt]`, and `CFRelease`s the CVMetalTextures in the completed handler. The code comment itself says a texture kept alive keeps its pixel buffer out of the pool. In the facade every bound texture goes through `track()`, so `rset` holds a +1 on `yt`/`uvt` until the ageing scan drops them (about 0.75-1.25 s after last use, mcm4.m:141-157). At 60 recorded fps that is 60-75 live pixel buffers against `kCVPixelBufferPoolAllocationThresholdKey = 16` (rec.m:361), so `CVPixelBufferPoolCreatePixelBufferWithAuxAttributes` returns would-exceed-threshold and `mcr_vt_capture` returns -2: about three quarters of ticks are dropped ("dropped" counter), the video repeats frames.
Fix: in the completed handler, before `CFRelease(ty/tuv)`, call `mc4_unpin(yt); mc4_unpin(uvt)` (no-op when Metal 4 is off). `releaseDying` then removes them as soon as the CB is done. (This is the general rule: anything not owned by Java through mc_release that wraps external memory must be unpinned explicitly.)

### A3. Opt-in `-Dcadence.lod.taaTile` crashes at the first frame with an unrecognized selector (low severity, certain)
lodseam.m:253 `[r dispatchThreadsPerTile:MTLSizeMake(r.tileWidth, r.tileHeight, 1)]`. McM4Render does not implement the `tileWidth` / `tileHeight` properties (clang with -Wobjc-protocol-property-synthesis lists both; the `-Wprotocol`/`-Wincomplete-implementation` pragmas at mcm4.m:24-26 hide this class of bug). `r` is the facade, so `-[McM4Render tileWidth]` raises. Besides: Metal 4 does not order a tile dispatch after earlier draws in the same encoder for you; it needs `barrierAfterEncoderStages:MTLStageFragment beforeEncoderStages:MTLStageTile` (the facade's `memoryBarrierWithScope:afterStages:beforeStages:` can emit it, lodseam.m never calls it).
Fix: add `- (NSUInteger)tileWidth { return r.tileWidth; }` and `tileHeight` forwards (MTL4RenderCommandEncoder has them), and a fragment-to-tile barrier in `dispatchThreadsPerTile:` in the facade (cheap, correct for every caller).
I diffed every selector the native sources send to command buffers / encoders / queues (clang AST dump, receivers typed id<MTL...Encoder/CommandBuffer/CommandQueue>): this is the only unimplemented one that the native code calls. Everything else (list at the end) is implemented.

### A4. MetalFX scaler is released immediately on size/format change while frames in flight still encode it (low-medium, resize / render-scale change)
MetalFxUpscaler.java:26-28 `release(); scaler = fxSpatialNew(...)` -> mcfx.m:48 `[scaler release]`. Metal 3 retained the scaler in the command buffer; an MTL4FX scaler encoded into an MTL4CommandBuffer is, per the same experiment as A1, not retained by the command buffer. MAX_IN_FLIGHT frames that used the old scaler are still executing. Scenario: change world resolution / drag the window with a pack at <100% render scale: one or two frames with garbage or a GPU error.
Fix: route the release through `encoder.releaseLater(...)` (Java) or push it on a native "dying objects" list gated on `completed`.

### A5. Argument tables are pooled without being reset: slots the new encoder did not bind show the previous encoder's bindings (low-medium)
mcm4.m:171-193. `takeTable` never sets `initializeBindings` and `giveTable` does not clear. Measured (tbl.m): a fresh table's unbound texture slot reads (1, 0.5, 1, 0.5); a recycled table's unbound slot keeps sampling the previous encoder's texture. Metal 3 returned zeros for an unbound slot. Anything that reads a slot the game did not bind (translated pack shaders declaring a sampler/texture the pass never sets; the cull kernels' "optional" slots, which mcown.m:1195-1202 already works around with a zero buffer) now sees stale data, and if the stale texture has since been freed and removed from the residency set the access is to non-resident memory (tbl2.m did not fault, but that proves little). Nondeterministic image differences between Metal 3 and 4 for such shaders are the symptom.
Fix: track a per-table high-water index for buffers/textures/samplers and write `{0}` over 0..max in `giveTable`, or bind the 4 KB zero buffer / a 1x1 null texture + default sampler to the high-water range. Cost is tiny because snapshots are taken per draw, so clearing after endEncoding is safe.

### A6. MetalHandles (Cadence API) hand addons facade objects typed as real Metal objects (medium for addon authors)
mcpack.m:139-148 `mc_api_handle` returns `ctx->queue` (McM4Queue), `enc->cmd` (McM4CB) and `enc->render` (McM4Render) when Metal 4 is on; MetalHandles.java documents them as `id<MTLCommandQueue>/id<MTLCommandBuffer>/id<MTLRenderCommandEncoder>`. An addon calling anything outside the implemented subset gets an unrecognized-selector exception: `setVertexBuffers:offsets:withRange:`, `setVertexBufferOffset:atIndex:`, `setFragmentTextures:withRange:`, `setViewports:count:`, `setScissorRects:count:`, `setDepthClipMode:`, `setStencilFrontReferenceValue:backReferenceValue:`, `setFragment/VertexSamplerState:lodMinClamp:...`, `useHeap(s):`, `textureBarrier`, `drawPatches...`, `sampleCountersInBuffer:...`, `presentDrawable:atTime:`, `[cb commandQueue]` (mcm4.m:528 returns nil), and `setBufferOffset:atIndex:` which deliberately `abort()`s the whole game (mcm4.m:429). Samplers must have been created with `supportArgumentBuffers = YES` or they bind resource id 0 silently. Also, the 4 KB `setBytes` limit no longer applies but the data lives only until the CB completes.
Fix: implement the cheap missing selectors (offset update = re-`setAddress` with remembered base; multi-range binds = loop; viewports/scissors/depth clip map directly), return the queue facade from `commandQueue`, replace the `abort()` with a logged no-op/forward, and document in docs/API.md and MetalHandles.java that under `-Dcadence.metal4=true` these are Cadence facades with an implemented subset (or expose `MetalHandles.metal4()`).

### A7. Direct `[obj release]` entry points bypass `mc_release` (low: delays frees, no leak found)
mcown.m:272 `mco_release`, mclod.m:35 `mcl_release` (used for all own-terrain and far-terrain buffers: OwnTerrain.java, OwnFrag.java, Lod*.java, LodClip.java:579-583) do not call `mc4_unpin`. These buffers are only ever `track()`ed (never pinned: `mc_buffer_gpu_address` is called only from MetalTerrain.java:424 on MetalBuffers released through mc_release), so they are not leaked: ageing frees them. But they stay alive 0.75-1.25 s after release instead of "as soon as the GPU is done", which is the point of the dying list (its own comment: 3 GB at 11,000 fps). Level change / disposeAll / buffer-growth bursts (A1 tables 2x8 MB, 64 MB class arrays) hold the old copies for a second.
Also native-internal `[x release]` of tracked resources (pkVis, soTex, hiz, taaTex, tileTex, r->copy, qUnits...) behave the same, which is fine. If any of these were ever passed to `mc_buffer_gpu_address` or `mc4_pin`, they would leak forever.
Fix: make `mco_release` and `mcl_release` call `mc4_unpin(obj)` first (two lines).

### A8. `setBytes` of more than 256 KB overwrites its own data when it is the first bytes of a command buffer (latent, unreachable today)
mcm4.m:238-243 and 250-253. The oversized path inserts its private buffer at index 0 of `chunks` and leaves `chunkUsed == 0`; if `chunks` was empty it is now the "current chunk" (`lastObject`), so the next small `setBytes` memcpy's at offset 0 of that big buffer, destroying the earlier big payload (and bounds are not checked against its size). Metal 3 limits setBytes to 4 KB so no caller does this, but addons now can (A6). Fix: append the big buffer to a separate `bigChunks` array or `addObject` and then force `chunkUsed = CHUNK` so the next call allocates a fresh chunk.

### A9. Queue-level wait/commit/signal sequence is not atomic; completion serials assume commit order = serial order (low, only if something commits off the render thread)
mcm4.m:655-680. `waitForEvent` / `waitForDrawable` / `[m4q commit:]` / `signalEvent` / `signalDrawable` are separate queue calls, and `serial = ++submitted` is taken under `rlock` but the queue commit happens after the unlock. Today `commit` is called from the render thread except `mc_buffer_private`, `mc_pc_buffer_new`, `mc_cull_new` (init/pack load) and `mcc_copy_out` (capture); `MetalCompute.buffer` goes through `RenderSystem.getDevice()` so it is render thread too, so I could not construct a concrete race. If any pack/asset loader ever commits from another thread: (1) its CB can pick up the render thread's pending `waitForDrawable` (so the loader CB stalls and the frame CB renders into an unavailable drawable); (2) serial N+1 can reach the queue before N, so `completed` (max of finished serials, mcm4.m:639-640) can claim N is complete while it still runs, and releaseDying/ageing may drop a resource it uses. Fix: one `commitLock` held over waits + serial + residency commit + `[m4q commit]` + signals (the residency commit is already serialised, so contention is nil).

### A10. Residency stamps are one commit behind when `pre` and `main` are open together (low, needs a >0.75 s GPU stall)
`track()` stamps `submitted + 1` (mcm4.m:58). Frame encoding opens `pre` and `main` together; both stamp N, but pre commits as N and main as N+1. The ageing snapshot `ageSerial[3] = submitted` (mcm4.m:145) is taken in main's `residencyBeforeCommit` after pre's `++submitted`, so it records N-1 or N (never N+1). After ~1 s, `limit = min(N, completed)` can drop a resource whose only user is main N+1 if N+1 has not finished. Only a one-second GPU stall (heavy pack at 4K, a pack-compile frame) hits it, and the resource must not be used again. The same off-by-one exists for `mc4_unpin` (`submitted + 1`, mcm4.m:83,90) if anything released a resource before the frame's commit; Java defers (`releaseLater` runs after the frame retires), so I found no instance.
Fix: stamp `submitted + openCBs` (count McM4CBs created and not yet committed; two lines in newCB/commit).

### A11. Hard-to-see range hazards: argument-table indices are unchecked (low, hardening)
`setAddress/setTexture/setSamplerState atIndex:` with an index >= 31 / 128 / 16 is documented "an error" for MTL4ArgumentTable (writes past the table) where Metal 3 silently rejected. Callers that can produce large indices: `mc_r_texture(enc, i, tex, sampler)` uses the texture index for the sampler too (mcmetal.m:1624-1631; Java passes `i` unchanged for non-pack pipelines, MetalRenderPass.java:315-316); `MetalStorage.BUFFER_BASE (16) + binding` (MetalStorage.java:72) reaches 31+ for binding >= 15; `VERTEX_BUFFER_BASE = 27`. Add `if (i >= max) return;` (with a one-shot log) in the facade setters, or size the table descriptor to the maximum and rely on the check.

### A12. Profiling / counters silently ignored under Metal 4 (info)
`renderCommandEncoderWithDescriptor`, `computeCommandEncoderWithDescriptor`, `blitCommandEncoderWithDescriptor` drop `sampleBufferAttachments` (mcm4.m:541-584, 599-601). `-Dcadence.metal.trace`, `encLog`, `own.gputime`, `lod cull timing` therefore report "no data"/zeros with Metal 4. Same for `rasterizationRateMap` (unused today). `-[McM4Render label]` returns nil, so `mc_profile_labels` loses native labels.

## B. Lower-confidence concerns

- B1. Layer residency set not attached. CAMetalLayer.h (26.0) says apps "should use" `layer.residencySet` so everything needed to render into or present drawables is resident; the facade never adds it (only the drawable texture goes through `track`). layer.m shows the layer set fills with 2-3 drawable textures only as drawables are handed out. No failure observed (you ran it), but the documented contract is not followed; the fix is `[ctx->queue addResidencySet:layer.residencySet]` in `mc_layer_configure` (re-add after the `layer.device = ...` assignment at mcmetal.m:1780, remove the old one) guarded by `respondsToSelector:`.
- B2. Global frame serialisation (performance, not correctness). The all-stages queue barrier at every encoder start (mcm4.m:258-260) removes the frame-to-frame and pass-to-pass overlap that Metal 3's per-resource tracking allowed; mcmetal.h:44-54 describes the old design as depending on exactly that overlap (pre CB vs previous frame). xcb.m shows the barrier does order across separately committed command buffers (200/200 ok with, 194/200 stale without), so correctness is fine. A cheaper first step: `afterQueueStages = Fragment|Dispatch|Blit` (producer stages), `beforeStages = Vertex|Dispatch|Blit` for encoders whose first stage is vertex/dispatch.
- B3. `completed`/`status` are written by the feedback thread without barriers while the render thread polls `status` (`mc_cmd_done`); `status` is set before `completed` and before the handlers run. Benign on arm64 for aligned words, but make `status` `_Atomic`.
- B4. Completion handlers now run inside `finished:` before `dispatch_group_leave`, so a slow handler (capture file writes in mccap.m, gpuCount reports) delays `waitUntilCompleted` waiters, allocator recycling and the `completed` serial. In Metal 3 handlers ran off the waiter's path. If handlers must stay ordered before waiters, at least move `completed` update and allocator recycle before them (the allocator/pool/serial update does not depend on the handlers).
- B5. Multi-context: `mc_create` called twice (headless tests, MetalBridge.createHeadlessContext) re-initialises every static in mcm4.m (`m4q`, `rset`, `tracked`, pools) and orphans the first context. Fine for single-context runs.
- B6. `mc4_unpin` serial semantics and `releaseDying` rely on `dying` pointers being used only as dictionary keys; I checked the order (releaseDying runs before ageing in the same commit, serials are non-decreasing) and could not make a dangling key remove a different live resource.
- B7. Autorelease pools: native entry points that return facade objects without an `@autoreleasepool` (mccull.m, lodseam.m, rec.m `computeCommandEncoder` calls, mc_pc_* etc.) leave an autoreleased 48-byte McM4Compute per encoder if the calling thread has no pool, exactly as the real Metal 3 encoders did (those were larger). `takeTable` also creates an autoreleased descriptor, only on pool miss.
- B8. `MTLCommandBuffer` semantic gaps not exercised by the native code: `waitUntilScheduled`/`enqueue` are no-ops, `status` never reports Enqueued/Scheduled, `kernelStart/EndTime` alias the GPU times, `presentDrawable:atTime:` missing, `useResidencySet(s):` missing, `errorOptions` fixed. Fine unless addons use them.
- B9. `mco_buffer(shared == 1)` hazard-untracked buffers are fine (Metal 4 has no tracking anyway); the "untracked" comments in mcown.m/mclod.m are stale but harmless.

## C. Checked and OK (so you do not re-check them)

Synchronisation
- Cross-command-buffer ordering: probe xcb.m (200 iterations, slow producer in CB1 committed first, consumer in CB2): barrier at the start of the consumer's encoder -> 0/200 stale; without it 194/200 stale. So pre -> main, previous frame -> next frame, mcc_copy_out, mc_pc_buffer_new / mc_cull_new fire-and-forget fills are all ordered by the encoder-start barrier.
- Concurrent compute encoders (mc_render_suspend and ownNextCompute): audited mccull.m encodePyramid/mc_cull_b_on, mcown.m mco_occ, ownPyramid (tiled, skip, gather, top variants), mco_frag_occ, mco_frag_uocc (all branches incl. rPyr/testOnly/uoccEnc), mco_quads_b, mco_qstats, mccap.m split copy: every producer->consumer pair inside one concurrent encoder has a `memoryBarrierWithScope` (mapped to Dispatch|Blit barrier); cross-encoder pairs get the start barrier. I found none that Metal 3 would have tracked and Metal 4 does not. Metal 3 does not track inside concurrent encoders either.
- Serial compute/blit encoders: AFTER_EACH covers dispatch, indirect dispatch, executeCommands, every copy/fill/mip/optimise. `memoryBarrierWithResources` over-approximates. OK.
- Render encoder -> compute -> reopened render (split passes): barrier at each encoder start orders the depth store, pyramid, args writes and reload.
- Fences: mclod.m `waitForFence/updateFence` are redundant behind the barrier and map to the right encoder stages; a wait on a never-updated MTLFence completes immediately in an MTL4 compute encoder (fence.m), so the first meshFences frame cannot hang.
- Events: `encodeSignalEvent` -> `[m4q signalEvent]` after commit orders after this CB (and any other thread's earlier commits: over-waits only); the only `encodeWaitForEvent` user (pqEncodePresent) runs on a plain Metal 3 queue, so the queue-level wait mapping is never exercised.
- MetalFX: fence-update encoder after a full barrier, scaler waits on it, next facade encoder's barrier covers the scaler's writes. OK (retention aside, A4).
- CPU readbacks: mc_buffer_private and mcc_copy_buffers_completed wait on the dispatch group, which is left after the feedback handler; mcr slot handlers set state after `status`. OK.

Residency
- Every bind, attachment, resolve, visibility buffer, index buffer, indirect buffer, copy source/dest, `useResource` goes through `track`; setBytes chunks and big setBytes buffers are pinned/tracked; the only GPU-address-only references (MetalTerrain arena tables) go through `mc_buffer_gpu_address` -> `mc4_pin`, and those buffers are released via `mc_release` (A7 analysed). No heaps, ICBs, argument buffers or acceleration structures in the native code.
- rs.m: a texture *view* in the set makes the whole parent resident and retained (allocatedSize equals the parent's, parent kept alive); a buffer-backed texture accounts the full buffer; a memoryless texture counts 0 bytes and adding it is accepted. So `track(view)`, `track(texture over buffer)` and memoryless attachments are correct.
- Ageing/dying bookkeeping (races, key reuse, order of releaseDying vs ageing, pinned entries) holds except the off-by-one in A10.

Semantics
- Samplers: all four creation sites in native code set `supportArgumentBuffers = YES` (mcmetal.m:72,374,393; mclod.m:137), Java only reaches them through mc_sampler_new / mc_sampler_new_compare (MetalSampler.java, Native.java:240-242). Creating 3000 distinct argument-buffer samplers did not return nil (samp.m).
- Table limits 31/128/16 equal Metal 3's per-stage limits; only the unchecked-index risk in A11 is new.
- Every selector sent to command buffers, queues and the three encoder kinds by mcmetal.m, mcown.m, mclod.m, mccull.m, mccap.m, mcpack.m, lodseam.m, rec.m, mcfx.m, mcbench.m (own device) is implemented, except tileWidth/tileHeight (A3). Full list of unimplemented protocol methods (compiler, mcm4_warn.m) is irrelevant to the native code but is the addon-visible gap (A6).
- `presentDrawable:afterMinimumDuration:` -> `presentAfterMinimumDuration:` after `signalDrawable`, `waitForDrawable` before commit: matches the documented MTL4 present sequence; `drawable.texture` set is small and stable (layer.m), no per-frame residency churn.
- `setBytes` alignment is 16 and the copy is immediate; Metal 3's `setBytes` also copied at call time. Bytes bound by address have no length: a shader that reads past the struct now reads the next payload instead of Metal 3's clamped/zero read (mc_r_bytes already pads to 16).
- Completed-handler ordering, `waitUntilCompleted` before commit (returns immediately), `GPUStartTime/EndTime` from the commit feedback: fine.

Threading / MRC
- `rlock` is not held across anything that can call back into the facade (the `removeAllocation` that may free an object is a plain dealloc); `plock` is leaf-level; `finished:` takes only `plock`. No lock-order inversion found.
- Retain balance: McM4CB retained by `commit` until feedback; encoders retain their MTL4 encoder and release at endEncoding; tables returned in endEncoding; pooled alloc/cb are shared between pool and CB (each holds its own reference). Uncommitted McM4CB deallocation with an outstanding `dispatch_group_enter` does not crash (dg.c).
