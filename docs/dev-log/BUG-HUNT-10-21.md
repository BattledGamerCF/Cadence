### Suggested order for fixing (my reading: severity, then how many players meet it, then cost)

1. **BH-12 and BH-14** (frame pacing, Heat hold): on a 60 Hz MacBook a Cooling hold or a Max Framerate of 40 or 50 delivers 30 fps, and the hold can start low and stay there. Small change in `FramePacing.cap` and the hold's start rule, large visible effect.
2. **BH-15** (about 470 or more animated sprites in one atlas end on the out-of-memory screen): heavy resource packs and modpacks. Move the rectangle table off the stack and catch the failure.
3. **BH-11** (`cadence.metal=false`, which Cadence also sets for Distant Horizons on OpenGL, plus any shader pack: JVM abort): grey out the Shaders button when the Metal backend is off.
4. **BH-01, BH-02, BH-07** (Vivace failure paths): only players who switched Java to Vivace, but BH-01 is a launch that never opens a window and BH-02 a Video Settings screen that cannot open.
5. **BH-09** (Render Max FPS: 30 s of "Loading terrain..." at every join and dimension change).
6. **BH-17, BH-18** (malformed pack resources abort the JVM instead of a clean refusal): pack authors and hostile packs; a few range checks before the native call.
7. **BH-22** (resource-pack PBR maps are ignored): a feature decision; at least document it, since a pack's "labPBR / seuspbr (RP required)" setting does nothing.
8. The rest (BH-03, 04, 05, 06, 08, 10, 13, 16, 19, 20, 21, 23) and the S-xx list as time allows. BH-16 and BH-19 only show with Metal's validation layer or an enforcing driver.

### What held up (so the fixing session does not have to re-check it)

- **Rendering correctness:** Cadence's own terrain against vanilla's on a block zoo of 1,264 block types, lossless pixel diff over 6 camera views: identical except animated sprites, one wolf and a particle (0.07-0.28% of pixels); the mesh, model, quad and text verifiers: 0 mismatches over 503,804 quads, 64 M faces, 25 M quads; Arabic and Japanese text through Cadence's text path: pixel-identical to vanilla's; entity and block-entity culling hid nothing that was visible (527 hidden behind walls under BSL, every visible stand and block entity still drawn). No visual corruption was confirmed in any run (hence none in the table).
- **Resources and options:** high-resolution block textures (128x and 256x: a 16384x8192 atlas, ~900 fps), a custom bitmap font, core-shader overrides (broken ones fall back through vanilla's own recovery), minimal / maximal / out-of-range graphics options, a 150-pack folder, symlinked packs, third-person views, an entity zoo of 88 mob types (212 million model faces verified against vanilla's writes, 0 mismatches) and a Save and Quit round trip of blocks, a chest, a sign and entities all behaved (see the coverage table).
- **Shader packs:** all 25 packs in the dev folder at noon and at midnight in rain: no crash, black or empty frame; the two refusals (Shrimple, Rethinking Voxels) are clean messages. Broken or odd packs (0-byte, garbage and truncated zips, folder packs, a folder without `shaders/`, unicode and spaced names, an invalid option) are refused with a readable chat line and the next pick works. Pack options pages, the Shader Packs screen, drag-and-drop, Quick Setup, the Benchmark and every Video Settings button behave as documented; a 640x480 window fits everything but BH-13.
- **Switching and memory:** 13 live pack switches, overlapping and rapid switches, quitting while a pack compiles or a benchmark runs: consistent final state, exit 0; GPU textures return to the same baseline after every "off"; no leaked client level over 3 leave / rejoin cycles; a 14-minute flight with pack switches kept the heap flat; G1 under Cadence's defaults had no Full GC or to-space exhaustion at 1 and 2 GB heaps.
- **Game logic:** 0 mismatches over 300,000 tick-range checks, 1.8 M path-cache hits, 20,000 queue polls (the developer's own verify switches), and the default-profile server-side mixins read against vanilla's bytecode (random ticks, POI scan order, region save skip, entity section order, particle collisions) without a difference.
- **Environment:** corrupt, out-of-range and non-UTF-8 config files, a Sodium conflict, an Intel Java and an old macOS, a fresh game folder, a game folder whose path has spaces, parentheses, an umlaut, apostrophes and an ampersand, a missing `java.io.tmpdir`, symlinked pack entries (see the coverage table), the 18-mod production set (two runs, the longer with 35 steps) and a LAN host with a guest: all clean or refused cleanly (except what is listed as BH-xx).

## Confirmed bugs

### BH-01 [hang, latent] Java switch: the probe's 20-second timeout is skipped, so a probed java that never exits blocks game start forever
- **Area:** Video Settings > Java / `dev.cadence.metal.Vivace.probe` (runs at the very start of loading, before any window).
- **Repro (offline harness, no game):** make a fake Vivace home (`bin/java` = `#!/bin/bash` + `sleep 300`, `release` with `JAVA_VERSION="25.0.5"` and `IMPLEMENTOR="Vivace"`), set `-Dcadence.java=<that bin/java>` and call `Vivace.target(gameDir, List.of("-Xmx2G"), List.of("-XX:+UseG1GC"))`. Harness: `scratchpad/bughunt/viv/src/dev/cadence/metal/VivaceHang.java`, output `scratchpad/bughunt/viv/hang.out`.
- **Evidence:** `hang (sleep child holds stdout): STILL BLOCKED after 30006 ms` (the harness gave up at 30 s; the call was still inside `readNBytes`). The same harness with output >= 8 KB then a hang returns after 20105 ms with "Vivace didn't answer in 20 s", so the timeout works only in that one case.
- **Cause:** `Vivace.java:178-186`: `in.readNBytes(8192)` is called before `p.waitFor(20, SECONDS)`. `readNBytes` blocks until EOF or 8192 bytes, so a child that neither exits nor writes 8 KB (and a child whose own subprocess keeps the pipe open) is never timed out. Real-world triggers: a Java that stalls on its first start (quarantined/unverified binary waiting on a Gatekeeper prompt, a stuck volume), or any wrapper script around java.
- **Effect:** Minecraft never gets to its first window; the launcher shows "playing" with nothing on screen until the child exits. Only with Video Settings > Java = Vivace (or `cadence.java=`).
- **Fix hint:** wait for the process with a deadline first (`p.waitFor(20s)`), read the output after, or read on a thread; destroyForcibly on timeout.
- **Real-world trigger, reproduced from a shell:** a scratch copy of the installed Vivace 25 runtime with the quarantine attribute set (`xattr -rw com.apple.quarantine "0081;5f000000;Safari;<uuid>"`, what a browser download gives it) was started with `java -version`: no output and no exit after more than 60 s (state S, I killed it), and macOS started `XprotectService` and `CoreServicesUIAgent` at that moment (Gatekeeper's check/prompt: an unnotarized, ad-hoc signed binary). INSTALL.md tells the player to clear the quarantine flag, but a player who doesn't will have Minecraft wait here: the probe has no working timeout, so the game never opens a window until the prompt is answered (then the process is killed and the 137 path gives the "macOS stopped Vivace" note, lost to BH-07). The `exitValue() > 128` branch the code has for this case is only reached after that.
- **Confidence:** high (the missing timeout reproduced offline; the stall of a quarantined Vivace reproduced in a shell; the launch itself with a quarantined Vivace was not run end to end).

### BH-02 [crash, latent] `Vivace.version()` fallback is itself invalid (`Runtime.Version.parse("0")` throws)
- **Area:** `dev.cadence.metal.Vivace` (installed(), target(), feature()), `CadenceSettings.javaButton`.
- **Repro (live, no real files touched):** scratch home `scratchpad/bughunt/fakehome/Library/Application Support/Vivace/` with two folders: `Vivace-25.0.5+8-fake.jdk` (valid release) and `Vivace-broken.jdk` (empty `release`, an executable `bin/java`). Run `CADENCE_EXTRA_JVM="-Duser.home=<fakehome>" CADENCE_RUN=<scratch run copy> tools/cadence-test.sh "wait=6,screen=video,wait=3,screen=close,wait=1" 3`. Result folder: `scratchpad/bughunt/run-b/results/1021-212012/`.
- **Evidence:** `latest.log:203`: `[Render thread/ERROR] (Minecraft) Error executing task on Client` / `java.lang.IllegalArgumentException: Invalid version string: '0'` at `Vivace.version(Vivace.java:239)`, `Vivace.installed(Vivace.java:78)`, `CadenceSettings.javaButton(CadenceSettings.java:366)`, `VideoSettingsScreen.addOptions`. The screen did not open. (The self-test opens it inside `mc.execute`, which logs and survives; a real click on "Video Settings..." runs `new VideoSettingsScreen` inside the mouse handler, where the same exception is a crash report. With ONE broken folder `Stream.max` never calls the comparator, so it only shows with two or more Vivace candidates.) Offline: a release with `JAVA_VERSION="banana"` throws the same way out of `Vivace.target`.
- **Cause:** `Vivace.java:235-241`: `version()` catches the parse error of a bad/missing `JAVA_VERSION` and returns `Runtime.Version.parse("0")`, which is not a valid version string and throws again (Java versions start at 1). ### BH-12 [perf, user-visible] Frame pacing turns a 45 or 50 fps cap into 30 fps on a 60 Hz screen

  |---|---|---|
  | 45 (`1022-010612` / `1022-010723`) | **30 fps**, frame interval 33.4 ms, 513 of 513 presents lasted 2 refreshes | 40 fps, 25.0 ms, 343 of 683 presents 2 refreshes (uneven, but 40 on average) |

- **Cause:** `FramePacing.cap` asks the display to show each frame for at least `0.97 / cap` seconds. A 60 Hz display only changes picture on a refresh (16.67 ms), so that minimum rounds up to whole refreshes: `ceil(0.97 / cap / 16.67 ms)`: 1 refresh for caps of 59 or more (60 fps), 2 refreshes for caps 30..58 (30 fps), 3 for 20..29 (20 fps). ### BH-14 [perf, high impact on a fanless 60 Hz Mac] The heat-control hold is set from a startup/loading frame rate and then stays

  3. `FramePacing` then delivers a 45 cap as 30 fps (BH-12); the toast and the Video Settings line ("Heat (Mac warm): holding ~45 fps") do not match the picture.

- **Confidence:** high for the 30 fps runs and the cap lines (logs), high for the code path.
- **Not tested:** a ProMotion display; whether the hold lifts after the Mac cools (no run was long enough); the deterministic repro attempts (`thermal=1` faked right after a join: `1022-022737`, `1022-022908`, `1022-023039` started at 60, 120, 120).

- **Cause:** the message is a constant: it names neither the directory (`Files.createTempDirectory("mcmetal")` uses `java.io.tmpdir`) nor `e`'s message; and because it is thrown from a static initializer, the cause chain does not reach the crash report (as seen here). Related: `getResourceAsStream` returns null when the jar lacks the native (a broken build), which would be an NPE from `Files.copy`, not an `IOException`, so it bypasses this message too.
- **Effect:** a player with a full disk or an odd temp folder gets a crash screen that does not say what to fix; support has to ask for the log. Rare, cheap to fix.
- **Fix hint:** build the message from the folder and the cause (`"can't extract libmcmetal.dylib into " + tmp + ": " + e`), catch `RuntimeException` too (null stream), and consider falling back to a folder next to the game (`<gameDir>/.cadence/natives`) when the temp folder is unusable.
- **Confidence:** high (reproduced).
- **Not tested:** a really full disk (the same `IOException` path, "No space left on device"), a `java.io.tmpdir` on a volume that disappears while the game runs (extraction happens once, at startup), an unreadable `libmcmetal.dylib` resource (a broken jar).

## Suspected, not confirmed

### S-01 `ShaderRuntime.instance` is a plain static (not volatile) but is read from other threads
`ShaderRuntime.java:53` (`private static ShaderRuntime instance;`, written by `install` on the render thread). `ShaderRuntime.get()` is also called from chunk-compile worker threads (`ShadowCompileCull.java:71`, `ShaderPipelineCacheMixin.java:26`) and the pack-switch worker. `TerrainShaderGeometry.configuration` right next to it IS volatile, so the intent was visibility. A stale `null`/old runtime on a worker after a live switch would mean one wrong cull/pipeline decision; not reproduced. Confidence: medium (race exists by the memory model, effect unproven).

### S-02 Quick Setup can leave the game on "Setting up Cadence..." forever if the test throws
`QuickSetupScreens.start` (`QuickSetupScreens.java:51-58`): the `cadence-quick-setup` thread calls `QuickSetup.run` with no try/catch; `run` only catches InterruptedException (`QuickSetup.java:141-143`). `MacSystem.benchGpu()` / `detect()` throwing (UnsatisfiedLinkError, NumberFormatException on an odd chip string, ...) kills the thread, and the GenericMessageScreen it set has no buttons and no Esc. Offered to every new player at the first title screen. Not reproduced (no way found to make `run` throw). Confidence: medium.

### S-03 HeapTrim overrides the player's own manageable GC settings
`HeapTrim.apply` (`HeapTrim.java:41-55`) sets `SoftMaxHeapSize`, `MinHeapFreeRatio`, `MaxHeapFreeRatio`, `G1PeriodicGCInterval` at run time whenever -Xmx > 1.5 GB and RAM <= 16 GB, without checking whether the player's Java arguments set them (JvmDefaults carefully respects the player's -XX options; this does not). Only `-Dcadence.heapTrim=false` opts out. Confidence: high that it happens; severity minor (design inconsistency).

### S-04 The client-side `/cadence` command swallows the same command on a server
`CadenceMessagesMixin.java:cadence$typed/cadence$clicked` cancel any `/cadence ...` the player sends (prints Cadence's own usage line) even on a server that has its own `/cadence` command. Cadence (the name) is also another mod's. Not reproduced.

### S-05 Failed Metal command buffers are never reported
No native code checks `MTLCommandBuffer.status/error` (`mcmetal.m`: completed handlers only measure time; `mc_cmd_done` counts Error as done). A GPU timeout/out-of-memory on an 8 GB Mac (BSL at RD 16) would show as garbage/black frames with nothing in the log. A diagnostics gap rather than a defect; could be logged once per session.

### S-06 `Level.tickBlockEntities` overwrite drops vanilla's profiler section
`LevelBlockEntityTickMixin.java` replaces the method without `profiler.push("blockEntities")/pop()`, so the F3 profiler/Tracy lose that entry whenever Cadence Logic's blockEntityTick is active. Cosmetic.

### S-07 (promoted to BH-20)
The Java button being ineffective when `cadence.java` is set in cadence.properties was confirmed live; see BH-20.

### S-08 FPS counter overlaps top-left mods
`HudMixin` draws "NN fps" at (2,2); with Xaero's Minimap (18-mod run) the text sits on the minimap's corner (`run-compat/results/1021-215645/selftest-0-start.jpg`). FPS Counter: Off is available. Cosmetic.

### S-09 Shader Packs screen: dropped files
`ShaderPacksScreen.onFilesDrop` (`:121-152`): a dropped zip whose name already exists is silently not copied but reported "Added <name>" and selected (a newer version of the same file never replaces the old one); the copy runs on the render thread (a 100+ MB zip freezes the window); a copy that fails halfway leaves a partial zip that is then never replaced (`Files.exists(target)`), and shows as a pack that "Couldn't load". The same-name part was seen live (scratch run `run-fresh/results/1022-011719`, step "drop the same zip again": "Added ..." and the pack is selected, nothing copied); the freeze with a large zip and the partial-copy leftover were not run.

### S-10 `Vivace.installed()` prefers the newest version, not the recommended one
With Vivace 25 and 27 both installed, 27 is picked (`Vivace.java:78`: newest first) while the changelog says Vivace 25 stays recommended; only `cadence.java=PATH` overrides. Design question.

### S-11 `ConfigFiles.store` uses one fixed temp name per file
`ConfigFiles.java:store` writes `<file>.tmp` then moves it. Two concurrent saves of the same file (settings are saved from the render thread and Cadence threads; `ShaderToggle.saveKey` is synchronized but `Vivace.save`, `PackCheck.save`, `PackSettingsScreen.apply` are not) could make the second move fail with NoSuchFileException (caught and logged, the change lost). Very unlikely.

### S-12 Shader Pack Settings: edits not yet applied are lost when the screen is closed by anything but Done/Esc
The settings are saved to `shaderpacks/<pack>.txt` and the pack reloaded by the Apply button (`PackSettingsScreen.java:170-172`) and by `onClose()` (`:333-335`, Done and Esc). If the screen is removed another way (the world closing under it, a death/disconnect screen replacing it, quitting the game with it open) the session's unapplied edits are dropped without a prompt. Cosmetic/minor; not run.

### S-13 CompatLayers treats every mod id starting with "cadence" as Cadence's own
`CompatLayers.java:apply`: `if (id.startsWith("cadence")) read(mod, ours)`. A third-party mod with such an id (another mod is called Cadence) would be read as Cadence's own hooks and never reported as a conflict. Not run.

### S-14 `Retina.on()` ignores the legacy settings file name
`Retina.java` reads only `config/cadence-shaders.properties`, while the Retina button and `ShaderToggle.retinaConfigured()` use `Legacy.readable` (also `minecraft-shader-loader.properties`); a hand-set `retina=false` in the old-named file shows "Restart Minecraft to turn Retina off" forever. Not run.

### S-15 `mc_fan_count` hands `b + 8` as the 32-byte output of `mc_smc_read`
`metal/src/main/native/mcsys.m:199`: `mc_smc_read("#KEY", b + 8, &type)` where `unsigned char b[32]` and `mc_smc_read` copies up to 32 bytes (`dataSize <= 32`). A `#KEY` reply longer than 24 bytes would write past the array on the stack. `#KEY` is a 4-byte count on every SMC seen, so harmless today; one-line fix (read into a fresh 32-byte buffer).

### S-16 (explained, not a defect) PotatoShaders' white band on the far horizon is the distance fog at the edge of the loaded terrain
Pack sweep `metal/run/results/1022-003913` step 14 shows a hard-edged white strip on the open ocean at render distance 6 (`scratchpad/bughunt/crop14.png`). Repeated at RD 6 / 12 / 16 (`1022-021535`, `1022-021715`, `1022-021854`, `g64-potato-rd.jpg`): the strip thins to a faint haze as the render distance grows, i.e. it is the pack's white fog meeting the void beyond the last loaded chunk, as in other fog-heavy packs. Kept here only so the question is not asked again.

### S-17 (promoted to BH-19)
The native animation copy's `setBytes` over 4 KB was confirmed with the Metal validation layer; see BH-19.

### S-18 `mc_pc_clear_texture` keeps its zero buffer forever
`metal/src/main/native/mcpack.m:93-107`: the static `zeros` buffer grows to the largest cleared texture slice and is never freed (a 4096 x 4096 RGBA32F custom image = 256 MB of shared memory until the game quits). The nil-buffer part of the same file turned out to be a real crash (BH-18).

### S-19 (promoted to BH-23)
The full path in the "Pack has no shaders directory" chat line, and the same for a missing file, were confirmed live; see BH-23.

### S-20 A failed Metal buffer allocation is never turned into an error: a nil buffer becomes address 0 and a native crash later
`metal/src/main/native/mcmetal.m:271-286` (`mc_buffer_new` returns whatever `newBufferWithLength:` gives, nil when the GPU/system can't provide it or the size is above `maxBufferLength`), `Native.java:198` (`bufferNew` hands the raw pointer back), `MetalDevice.java:182` and `:196` (`new MetalBuffer(encoder, Native.bufferNew(...), usage, size)`, then `MemoryUtil.memCopy(..., buffer.address, ...)` on the `createBuffer(label, usage, ByteBuffer)` path) and `MetalBuffer.java:72` (`rename()`): none checks for handle 0. `[nil contents]` is NULL, so the first write through the buffer faults inside the JVM (SIGSEGV) instead of an `OutOfMemoryError` with a message. BH-18 is the same pattern reached from a shader pack; this is the same hole for the game's own buffers (large render distance plus a heavy pack on an 8 GB Mac, the arenas and chunk buffers). Not reproduced (needs real GPU memory exhaustion). Fix: check the handle in `Native.bufferNew` / the native function and throw.

### S-21 (explained, not a defect) Insanity Shader Universal is almost black at night: its own night light is under 1% of full
Night sweep `metal/run/results/1022-020645`, step 10 (midnight, rain): the whole picture is black (mean luminance 9/255, 95% of pixels below 12; every other working pack shows at least the coast and the water; vanilla at the same hour: 23/255). Follow-ups:
- A clear midnight (`1022-025832`: `time=18000`, no rain; `g67-insanity-clear.jpg`): Insanity is still black (mean 10.0/255, 95% below 12), while Photon at the same clear midnight is normal (mean 25.6 vs vanilla 26.4: coast, clouds and moonlit sea visible), so Photon's dark rainy night was the weather and Insanity's darkness is the pack's own.
- The pack's source (`shaders/lib/color/lightColor.glsl`): night light and ambient are multiplied by 0.3 and then squared; with its defaults (night light (120, 80, 44)/255 x 0.65 x 0.3, ambient x 0.60 x 0.3) that is 0.8% / 0.4% / 0.1% (red / green / blue) of full light, against 1.3% / 5% / 9% for BSL's own night ((96, 192, 255)/255 x 1.0 x 0.3, squared), the pack Insanity is based on.
- With the pack's two night sliders raised to the top of their range (`LIGHT_NI=4.00`, `AMBIENT_NIGHTI=4.00` in a scratch copy of `shaderpacks/Insanity-Shader-Universal-v1.650.zip.txt`), the same scene at the same time shows the coast, terrain and clouds in a warm brown moonlight (run `scratchpad/bughunt/run-b/results/1022-031311`, mean 40.2/255, 4% below 12, `g72-insanity-boost.jpg`): the pipeline draws the night correctly; the pack is simply tuned very dark. Not compared with Iris.
