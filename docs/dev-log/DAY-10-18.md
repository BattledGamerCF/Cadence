# Day 2026-10-18: easier shaders, 13 more packs, a GPU pass

Asked for, in order: make shaders (and every menu) easier and less confusing after an audit; download and test more
shader packs for compatibility; then a GPU optimization pass for shader packs. M2 MacBook Air, the user's GUI scale 4,
short runs (the Mac was in use; the memory guard stopped one run for swap growth from other apps).

## 1. Menu audit

Walked every screen a player touches to use shaders, at GUI scale 4, with BSL on (self-test UI tour: Video Settings,
tooltips, Shader Pack Settings, Quick Setup). What was confusing:

| Before | Why it confused | Now |
|---|---|---|
| "Shader Pack: X" cycled one pack per click, applied when Video Settings closed | pack 10 of 12 took 10 clicks; nothing happened until you left; no way to see what's installed | **Shader Packs screen**: the whole folder as a list, click one to turn it on (O in game opens it) |
| A pack that failed said so once in chat | gone when the chat scrolled; the button still showed the pack | the list shows "Couldn't load: reason" under it for the session |
| No hint which packs work with Cadence | 23 tested packs, nothing in the game said so | "Tested with Cadence · Light/Medium/Heavy · note" or "Not tested with Cadence yet" (PackCatalog) |
| Separate Live, Quality and Folder buttons | three buttons for one decision; "Live" meant nothing to a player | gone: switching is always live when it can be, "restart to turn on" otherwise; Profile and Open Packs Folder in the list's footer |
| Shader options below the performance ones | the thing most players came for was at the bottom | Shaders and Shader Pack Settings first, then Performance and Quick Setup, then two labelled Cadence groups |
| "Pack Speed-ups: Built In / Check Now / On (checked) / Can't Tell" | didn't say what it speeds up (skipping shadow work), and long at GUI 4 | **"Faster Shadows: On / Test / Testing / Not Safe / Unsure / No Pack / No World"** |
| Pack Settings: change, Done, reopen to try again | no way to see an option's effect while choosing | **Apply** on every page; Reset at the top; one hint line (click: next, Shift-click: previous) |
| Graphics API option clickable | choosing OpenGL/Vulkan did nothing under Cadence | greyed, reads "Graphics API: Metal" |
| Status lines: "Cadence: automatic tuning ...", "Auto: world drawn at N% to keep it smooth", a raw compatibility list | several long lines, one per thing tuned | "Tuned automatically: resolution · cooling · background fps", heat and memory when relevant, "Works alongside: mods" |
| No keys | Iris users expect O and K | **O** opens Shader Packs, **K** toggles shaders off and back to the last pack (Controls > Miscellaneous; no Fabric API needed: mixins on Options.load and Minecraft.handleKeybinds) |
| Adding a pack: find the folder | Finder trip | drop .zip files (or folders with `shaders/`) on the list; the first one turns on; a zip that isn't a pack is refused with a message |
| No packs installed | an empty button | the list says how to add one; the button reads "Add Packs..." |

Checked in game (self-test steps `screen=packs`, `packpick=NAME`, `drop=PATH`, `key=NAME:press`): switching from the
list, K off and on, O with the in-use pack highlighted, dropping a non-pack zip, Apply in Pack Settings, the greyed
Graphics API row, and the empty state in a production launch with no packs.

## 2. Thirteen more packs

Details, per-pack fixes and GPU times: ../SHADER-PACKS.md (10-18 section). Summary: 11 of 13 work (Noble with shaded
sides darker than intended), so 23 of the 25 tested packs. Shrimple and Rethinking Voxels need geometry/tessellation
shaders; the list says so in plain words.

Bugs worth remembering:
- `sampler3D` goes through set 1 (storage) in Cadence's Metal layout, so 3D textures were never bound: Photon's sky
  read black (then sepia with the wrong filtering). `storageHandle()` now resolves a pack volume by program and sampler.
- `gcolor` is the block atlas in world programs (OptiFine): Nostalgia and Vanilla Plus drew every block as a flat colour.
- Metal's float3 in threadgroup memory is 16 bytes: Photon's 27 KB of shared vec3 became 36 KB, over Apple's 32 KB.
- Mellow names a varying `Normal` and an output `Color`, the adapter's vertex input names.
- Census false blockers: `textureLod`/`textureGather` on shadow samplers are fine with hardware comparison.

## 3. GPU pass

Kept: feedback copies only for samplers a program's code reads (Complementary Reimagined 44 -> 41 ms at 2940x1686, two
in-run A/Bs; 12 copies a frame to 2; BSL and Photon unchanged; pictures alike). Dropped with numbers: learned pass-clear
flushing (slower), relaxed shadow vertex math (noise), the read analysis for per-frame decisions (broke AstraLex, no gain).
Details in ../SHADER-PACKS.md.

Measurement notes:
- The fanless Air slows after ~2 minutes of full GPU load: Vanilla Plus read 31 ms late in a sweep and 12.4 ms in a short
  one. Sweep anchors (BSL, VanillaEX, Bliss) only help at the start; for a cost table, keep runs under 2 minutes or
  interleave an anchor.
- Self-test lines report the 10 s before the step's end: after `PACK,wait=12` the `wait` line is the pack's steady state.
- Auto resolution hides cost (every pack lands near 60 fps); use `-Dcadence.shaders.renderScale=0.5` for comparisons.

## 4. Dynamic Lights (afternoon, asked for)

Video Settings > Cadence: Performance, "Dynamic Lights: Off / Held Items / All" (off by default; DynamicLights,
DynamicLightList, four small mixins).

- **Terrain on the GPU.** Cadence's terrain vertex stage already samples the lightmap per vertex (terrain.metal
  ownShade), so the frame's sources (the 16 nearest to the camera, camera-relative, in the DrawFrame bytes every own
  draw already sets) raise each vertex's block light to `level - distance`, as a placed light falls off. Nothing is
  rebuilt when a light moves; LambDynamicLights rebuilds the chunk sections around each moving light instead. Light
  passes through walls, as in LambDynamicLights. DrawFrame grew from 80 to 368 bytes; mcown.m's 256-byte copy buffer for
  table/fallback draws had to grow with it (it skipped the copy, and so the draw, for a frame that didn't fit).
- **Everything else on the CPU, where its light is looked up**: EntityRenderer.getPackedLightCoords (final, so every
  entity, the hand and the held item), BlockEntityRenderState.extractBase, Particle.getLightCoords. Packed light carries
  1/16 levels, so these are smooth too.
- **Sources**: held items of every living entity (a block item's block as placed, plus lava bucket 15, blaze rod and
  fire charge 10, glow berries / glow ink sac / nether star 10, glowstone dust / blaze powder / magma cream / spectral
  arrow 8); fire goes out under water. All adds burning entities 15, item entities, item frames, falling blocks, an
  enderman's carried block, blaze 10, magma cube 8, fireballs 12-14, lit TNT 10, spectral arrow 8, glow squid 8, end
  crystal 10.
- **Off with a shader pack** (the pack draws terrain with its own programs, and the popular packs read
  heldBlockLightValue for their own held light, which Cadence supplies), without the own renderer, and with
  LambDynamicLights installed (button greyed, says so).
- **Cost** (in-run A/B, `ab=dynlights`, 16 sources: a torch and 15 floating glowstones, render distance 12, Retina):
  first version GPU +0.41 ms (1.87 -> 2.28); with a bounding-sphere test before the loop (most vertices are out of
  every light's reach) and no square root for sources out of reach, **+0.07 ms**; render thread +0.016 ms (noise).
- Checked at midnight in game: torch held / not held, third person, All with floating glowstone, the button at GUI 4.

## 5. Optimization round: smoothness (afternoon)

Measured first: a flight over new terrain (self-test `glide=40:1:120`, now held at a height and with its per-tick
command output suppressed: it had flown the player into a hillside, and a chat line per tick was most of the render
thread's garbage), a crowded scene (`scene=busy`), JFR (CPU and allocation, 1 ms sampling) and FrameLog lined up per
frame (`spikes.py`-style: the render thread's samples inside each slow frame).

**GC Remark pauses (kept, the big one).** Flying, G1 ran a marking cycle every 2-3 s; each ended in a Remark pause of
10.7 ms on average, 24.9 at most (16 per minute), 19 ms of it "G1 Complete Cleaning": class unloading walks all the
game's compiled code. `-XX:-ClassUnloadingWithConcurrentMark` (classes left to full collections; the game hardly unloads
any): **Remark 1.0 ms average, 1.9 max**, total pause time over the flight 563 -> 442 ms. Without class unloading at
marking, the Metaspace thresholds during loading became full collections (four of 15-29 ms in the first 3 s):
`-XX:MetaspaceSize=256m` (the game settles at ~170 MB; it only moves the trigger). Both in JvmDefaults, applied by its
existing restart. In the crowded scene Remark is 0.5 ms and young pauses 2.4-3.3 ms (max 4.9).

**Render-thread garbage (kept).** Crowded scene: 355 KB a frame (~177 MB/s at 500 fps), a young collection every couple
of seconds. Now 298 KB (-16%): MetalRenderPass's two ~160-slot uniform arrays reused through the encoder and its texel
view map made only when needed; FeatureGroupTagMixin skips partitioning when nothing is tagged (no pack); a model part
without children gets the shared empty iterator; one reused quaternion in translateAndRotate and one scratch vector in the
cube writer (render thread only). Meshing workers: the lighter-cache hooks were cancellable injects that boxed every
answer (a Float or Integer per lookup, ~3% of all garbage while flying): now @WrapMethod returning primitives. Pictures
of the crowded scene alike (mob models intact; the differences are smoke and animation).

Measured and not kept:
- `-XX:MaxGCPauseMillis=12`: G1 kept a 224-380 MB young generation; mixed pauses 10.5 ms avg, 19.4 max. No change.
- `-XX:ParallelGCThreads=4` (performance cores only): pauses longer (mixed 6.1 avg, 8.7 max against 3.3 / 4.9).
- Not built: pooling world generation's ore-vein density arrays (MaterialRuleContext.getDensitiesInChunk, ~7% of the
  flight's garbage, only while generating new terrain); a time budget for chunk packets on the render thread (5-9 ms
  bursts while flying fast; the client's chunk-batch rate feedback to the server would slow chunk loading with it);
  pooling submitted poses (lifetime across the frame graph).

What's left in a flight (42 s, render distance 12, 20 blocks/s, Retina): 13 frames over 16 ms, 8 over 25 ms. Most are
the GPU taking 4-7 ms instead of ~1.9 for a few frames in a row (other apps drawing: the Mac was in use) or young
collections during world generation (6-18 ms, promotion of new chunk data). Note for measuring: the self-test's
screenshot and memory census make spikes of their own every step; the test window not being the active app adds runs
of 8-12 ms frames with ~1 ms of CPU (macOS throttling the background app), not seen in real play.
